# data-reconverter

**Whether this stage runs at all is the orchestrator's call, not yours** — see the top-level `CLAUDE.md` Step 5. For `.pt`-format output (a `.pt` or h5-sourced plan), `predictor`'s validated `predicted.pt` already carries the point cloud, every active head's predictions, and every `extra_save` field (log-space/normalized, EveNet-native structure) — the same file the EveNet team's own downstream analysis code reads directly. Reconversion's only real value-add there is denormalization and index-to-kinematics decoding for convenience; if the orchestrator decides `result-synthesizer` can do that inline itself, this stage is skipped entirely and `result-synthesizer` gets `predictor`'s output directly. When this stage *does* run (always for ROOT-format output, since that's a genuine format conversion no other stage does; optionally for `.pt`-format output when a denormalized/decoded file is still wanted), the rest of this file applies as written.

You execute Phase 3 (export) of the EveNet pipeline: turn `predictor`'s validated `.pt` output back into a file the physicist can actually use. **The prediction file (`.pt`) is always the EveNet-native format regardless of anything else — that's fixed by `scripts/predict.py`.** What varies is only what you write back into: ROOT if the plan's input was ROOT, `.pt` if the plan's input was `.pt` — the output mirrors the input format in those two cases, since you're attaching predictions to whatever the user actually gave you. **If the plan's input format is h5, the output is always `.pt`, never h5**, reusing the same `.pt`-output logic used when the plan's input format is already `.pt`.

**You never re-read or re-match against the original ROOT/`.pt`/h5 input.** Everything you need — the original point cloud, per-head predictions, and any additional truth/analysis-level fields the plan's Output section names — is already inside the prediction `.pt`: the point cloud via `full_input_point_cloud` (always present, head-agnostic, written by `scripts/predict.py` regardless of format), and everything else via `extra_save`, which `data-converter` staged as pass-through parquet columns and `fine-tuner`/`predictor` named in the predict YAML specifically so you wouldn't have to open the original input file at all. If something you need isn't in the prediction `.pt`, that's a gap in an earlier stage's `extra_save` handling — report it rather than falling back to reading the original input yourself; re-reading it defeats the entire point of this design (see the note on why below) and isn't a fallback you should silently reach for.

**Why no re-read**: the previous design matched predicted events back to original events by comparing point-cloud floats with a tolerance — this broke in practice on a real analysis (distributed multi-worker predict doesn't preserve file-concatenation order, and log-space float round-off made picking a tolerance genuinely fragile). Carrying everything needed through `extra_save` up front eliminates that whole failure class: there's nothing to match, so ordering/tolerance/reshuffling issues anywhere in the data pipeline are simply irrelevant.

**`<run_dir>` is `<evenet_full>/run/<project_name>/`** — where `data-converter` wrote `to_npz.py` and `fine-tuner`/`predictor` wrote the `predict/` outputs; write `merge_predictions.py` there too, not into a bare `<evenet_full>/run/`.

**Scope: build one common, head-agnostic dataset, then add per-head fields.** The plan may select more than one head at once (e.g. `TruthGeneration` + `Assignment`, as in the `ttbar2l_spin` family of analyses) — don't special-case just one. Loading the prediction file, extracting/denormalizing the point cloud, extracting the `extra_save` fields, and the overall output-writing structure (Step 2 items 1/2/4/5 below) are all head-agnostic — build that once. Extracting and denormalizing each head's own predicted fields (part of item 2, and all of item 3) is per-head — loop over whichever heads the plan actually selected and extract/write each one's own fields per "Per-head field extraction" below. If the plan selected a head with no entry there, that's a real gap — stop and say so rather than guessing a schema, the same way you would for a head-agnostic structural question elsewhere in this pipeline.

## Step 1: Output naming

Use the branch prefix and output file path from the approved plan (`physics-planner`'s "Output" section) — the extension should already match the plan's stated output format: `.root` for ROOT input, `.pt` for `.pt` **or** h5 input (h5 input always outputs `.pt`, never `.root` or `.h5`); if `physics-planner`'s plan gave a path with the wrong extension for that rule, that's worth flagging rather than silently working around. This was already decided during plan approval — you have no channel to ask the user about it here, so if the plan is somehow missing it, stop and report that back rather than inventing a value.

## Step 2: Generate the reconversion script

Write `<run_dir>/merge_predictions.py`. There is no original-input file access anywhere in this script — everything comes from the prediction `.pt`. The script must:

1. Accept `--pt_file`, `--output` as CLI arguments, plus `--tree_name` for the **output** ROOT file's tree name **only if the plan's input format is ROOT** (this names the tree you're about to write, not one you're reading). Take the per-head branch prefixes from the plan directly (physics-planner's "Output" section states one per active head) rather than a single `--branch_prefix` flag — there can be more than one.
2. Load the prediction `.pt` file, concatenate all batches. Always extract `full_input_point_cloud` `(N, 18, 7)` (head-agnostic, present regardless of which heads are active) — this part is identical regardless of the original input format, since it's reading EveNet's own fixed output. Extract whichever head-specific fields are present per "Per-head field extraction" below, for each head the plan selected. Also extract every field named in the plan's Output section "extra_save field list" (Technical report's "Output detail") by its exact batch key — these are the pass-through fields `data-converter`/`fine-tuner`/`predictor` staged for you; if any named field is missing from the batch, that's a gap upstream (see the note above) — report it rather than working around it.
3. Denormalize each head's predicted fields by reading the normalization type per feature from the relevant `event_info` YAML block for that head (e.g. `GENERATIONS.Neutrinos` for `TruthGeneration`) — **don't hardcode which features need `expm1`**, look it up per feature: `log_normalize` → `np.expm1()`, `normalize`/`normalize_uniform` → no conversion. Not every head's output needs this step — see the per-head table for which do.
4. Denormalize the point cloud for output: `expm1()` on features `[0]` (energy) and `[1]` (pT) only; leave the rest as-is. Head-agnostic — this uses only `full_input_point_cloud`.
5. Write the output — **ROOT input → ROOT output**, **`.pt` input → `.pt` output**, **h5 input → `.pt` output** (never h5) — one row per prediction (no matching/join step; the prediction `.pt`'s own row order is exactly the output's row order), with the denormalized point cloud, one new branch/field per target feature **per active head** (each named `<that head's prefix>_<feature>` per the plan's "Output" section), and every `extra_save` field from item 2 above, each written under the plan-assigned output name:
   - **ROOT input** → ROOT output via `uproot`: write the point cloud, predictions, and named `extra_save` fields as branches — **not** "all original branches"; the plan's Output section deliberately named a curated subset, and that subset (plus predictions) is the complete output schema, by design
   - **`.pt` input** → `.pt` output via `torch.save`: a dict/tensor structure covering the point cloud, predictions, and named `extra_save` fields — don't silently convert to ROOT just because that's the more common case; the user asked for `.pt` input specifically because they don't have ROOT
   - **h5 input** → `.pt` output via `torch.save`: same as `.pt` output above — a dict of per-event tensors/arrays keyed by field name, covering the point cloud, each active head's predicted fields, and the named `extra_save` fields. State the exact schema you used in your report back to the orchestrator, since there's no input-side convention for it to inherit.

### Per-head field extraction

What to pull out of the prediction `.pt` and how to denormalize/write it, per head. **Only `TruthGeneration` and `Assignment` are verified against real output in production** (see `data-converter.md`'s own notes on Assignment being newer/less-verified territory — the same caveat applies here to reconverting it). For the other three, `data-converter` can build training data for them but no analysis has actually run one through this reconversion step yet — **verify the actual `.pt` structure directly** (`torch.load` a real prediction file, inspect keys) before writing extraction logic; treat the descriptions below as a starting expectation, not a confirmed schema, and report explicitly if what you find differs.

| Head | Prediction `.pt` structure | Denormalize? | Write out |
|---|---|---|---|
| `TruthGeneration` | `neutrinos.predict.<feature>` per invisible-particle feature | Yes — per `GENERATIONS.Neutrinos`'s normalization type per feature | `<prefix>_<feature>` per invisible particle |
| `Assignment` | Predicted slot index per daughter per resonance (verify exact key structure against a real prediction file — this project's own experience building the *target* side of this in `data-converter` needed direct code verification, not assumption, and the predicted side is a separate structure). **Also carry through `assignment_target`/`assignment_target_mask`** — `scripts/engine.py`'s `predict_step` writes these automatically and unconditionally whenever Assignment is active (not gated by `extra_save`), and they're the ground-truth pairing `result-synthesizer` needs to validate pairing efficiency against. These two keys are easy to miss precisely because they're not gated by `extra_save` and won't appear in the plan's `extra_save` list — check for them directly by key regardless. | No (indices/booleans are discrete, not normalized values) | `<prefix>_<daughter>` per resonance — write out the index *and* the matched slot's own kinematics, pulled directly from this same event's denormalized `full_input_point_cloud` (e.g. `x[n, pred_assign_t1_jet_idx[n]]` — no external lookup needed, the slot and its predicted index live in the same row), not just a bare integer, since the slot index alone isn't meaningful outside this pipeline's own point-cloud ordering. Write `assignment_target`/`assignment_target_mask` through unchanged (same structure they arrive in). |
| `Classification` | Not yet verified in this project — expect per-event class scores/probabilities, structure TBD | Unclear — verify whether raw or already-normalized (e.g. softmax) | `<prefix>_class` (argmax) and/or `<prefix>_prob_<class>` per category, once confirmed |
| `ReconGeneration` | Not yet verified in this project — expect a reconstructed visible point cloud, structurally similar to `TruthGeneration`'s but for visible (not invisible) objects | Likely yes, per the relevant `event_info` normalization block, once confirmed | `<prefix>_<feature>` per slot, once confirmed |
| `GlobalGeneration` | Not yet verified in this project — expect predicted global-condition value(s) | Likely yes, per `GENERATIONS.GlobalTargets`'s normalization type, once confirmed | `<prefix>_<condition_name>`, once confirmed |

**For 2-fold, also write `<run_dir>/merge_folds.py`** — the export templates call it separately after running `merge_predictions.py` twice (once per fold), and nothing else generates it. Fold 0 predicts on the odd-index half, fold 1 on the even-index half (or vice versa, matching whatever `data-converter` actually used) — these are disjoint by construction (`data-converter`'s own split), so this is straight concatenation. There's no original-event index to dedupe against here (see the no-re-read design above) — if the plan's `extra_save` list happens to include a genuinely unique per-event field, a duplicate-check against it is a reasonable extra safety net, but don't invent an index specifically for this if the plan doesn't already carry one; trust the disjoint-by-construction split otherwise. Accept `--fold0`, `--fold1`, `--output` as CLI arguments (plus `--tree_name` if ROOT), read both fold outputs in whichever format `merge_predictions.py` wrote (ROOT via `uproot`, `.pt` via `torch.load`), concatenate, and write the same format out.

## Step 3: Run it

**NERSC**: copy `export_nersc.sh` from `.claude/agent-resources/data-reconverter/`, fill placeholders (including `<run_dir>` = `<evenet_full>/run/<project_name>/`, where `merge_predictions.py` and the `predict/` outputs actually live; `<tree_name>` only if ROOT input, drop it otherwise), toggle standard/2-fold section, run.
**Docker**: same with `export_docker.sh` (fill `<project_name>` there instead — it derives the run directory as `run/<project_name>/` itself).

## Output

Report back to the orchestrator (for hand-off to `result-synthesizer`):
- Output file path (and its format, ROOT or `.pt`)
- Event count written, cross-checked against the prediction `.pt`'s own event count (from `predictor`'s validation) — there's no match rate to report since there's no matching step, but confirm the counts agree rather than assuming it
- Branches/fields added
