# predictor

## Default flow: validate, don't resubmit

In the standard pipeline, `fine-tuner` already ran `scripts/predict.py` as the second half of its combined submitted job — running prediction again here would waste a second queue wait for no benefit. Your job in this case is to **validate** the prediction output, not regenerate it:

1. Confirm the `.pt` file `fine-tuner` reported exists and is non-empty.
2. Load it (`torch.load(path, map_location='cpu', weights_only=False)`) and check the structure is what `data-reconverter` will expect: a list of batch dicts, each containing `neutrinos.predict.<feature>` keys matching the plan's target features, and `full_input_point_cloud` with shape `(batch_size, 18, 7)`.
3. **If `Assignment` is among the plan's selected heads, also confirm `assignment_target` and `assignment_target_mask` are present in every batch.** `scripts/engine.py`'s `predict_step` writes these automatically and unconditionally whenever the Assignment head is active (`convert_target_assignment(...)`, not gated by `extra_save` at all) — this is the ground-truth pairing, exactly analogous to how `neutrinos.target` is the ground truth for `TruthGeneration`. It's easy to miss precisely because it isn't named in the plan's `extra_save` list the way pass-through fields are — check for it directly by key, don't assume it's absent just because nothing asked for it. If it's genuinely missing (verify against `scripts/engine.py`'s actual current logic before concluding this, since this project's own EveNet-Full checkout can be updated independently of these instructions), report that explicitly — downstream (`result-synthesizer`) needs this for pairing-efficiency validation and must not fall back to reconstructing ground truth via ΔR-matching or any other heuristic when the framework already computed and shipped it.
4. **If `Classification` is among the plan's selected heads, confirm both (a) the predicted output and (b) a usable ground-truth label are actually present — these are two separate checks, and (b) is the one that's easy to get wrong.** For (a): `outputs["classification"]` is a dict keyed by the plan's classification target name(s) (e.g. `"classification/<name>"`), holding raw pre-softmax logits, shape `[B, num_classes]` — confirm it's present and the class count matches the plan's label definition; apply `softmax(..., dim=-1)` yourself when checking values, since the raw output isn't already a probability. For (b), the ground-truth class label is **not** analogous to Assignment's automatic pass-through — it does not ship into `predicted.pt` for free. The truth label's batch key (`self.target_classification_key`, typically the literal string `'classification'`) is the **same name** `scripts/engine.py` uses for the model's own predicted-output dict, so listing it in `extra_save` verbatim does not work as a naive copy would for another field — the predicted-output assignment already happened earlier in `predict_step`, and extra_save's `outputs[key] = batch[key]` would silently clobber the predicted logits with the truth label under that shared key, destroying the prediction rather than adding the truth (found the hard way on a real analysis — confirm this collision still exists in the current EveNet-Full checkout rather than assuming it, the same way you'd verify any other framework-internal behavior against live code). So: check whether the plan's Output section names a distinctly-named pass-through field for the true class label (e.g. an int64 category id under its own name, or a process/sample identifier field) — if the plan doesn't name one at all, or names one that turns out not to actually exist in the batch dict under that literal key, that's a genuine gap: report it explicitly rather than assuming `result-synthesizer` can recover true-class information some other way (e.g. from `assignment_target_mask`, which is not a valid substitute — a real signal event can have all-invalid assignment masks too, if truth-matching failed for every resonance, so mask-validity alone cannot stand in for true class membership across the full population).
5. Sanity-check value ranges aren't obviously broken (e.g. not all-zero, not all-NaN, roughly consistent magnitude with what log1p-space energy/pT values should look like).
6. For `2fold` only: confirm both fold `.pt` files exist and validate both. For `standard`/`holdout` there is exactly one prediction file — do not expect or wait for a second.

If validation fails, don't silently pass it downstream — diagnose (check the job's stdout/stderr log) and either fix-and-rerun the predict step yourself (see below) or report the failure clearly.

## Standalone flow: generate and run/submit prediction only

If invoked without an upstream `fine-tuner` job in this same run (e.g. the user wants a new prediction from an existing checkpoint, or `fine-tuner`'s validation above failed and needs a rerun), generate the predict YAML from `.claude/agent-resources/fine-tuner/predict-template.yaml` (the single shared copy — `fine-tuner` uses the same file; there is deliberately no separate `predictor/` copy, so a fix benefits both) if it doesn't already exist, filling paths under `<run_dir>` = `<evenet_full>/run/<project_name>/` (the same project-scoped directory `data-converter` and `fine-tuner` already used — don't write into a bare `<evenet_full>/run/`). Same `extra_save` requirement as `fine-tuner.md` Step 3 — this is the *only* way `data-reconverter` gets anything beyond the point cloud and per-head predictions (it never re-reads the original input), so add the plan's complete "extra_save field list" (Technical report's "Output detail"), not just an occasional validity field, if the plan names any.

**Same `default:`-field verification `fine-tuner.md` Step 2 requires, applied here too — don't just fill in the named placeholders above and assume the rest of the template is correct.** Check all four `default:` fields (`options.default`, `network.default`, `event_info.default`, `resonance.default`) resolve to absolute paths, not relative strings or unsubstituted template literals — `evenet/control/global_config.py` resolves each one relative to *this file's own directory* (`<run_dir>/config/`), so any left wrong crashes `scripts/predict.py` at config-load time before anything runs. This is the **same** template file `fine-tuner` uses (`.claude/agent-resources/fine-tuner/predict-template.yaml`) — there is intentionally only one copy, so a fix made for either agent applies to both. Still verify the four `default:` fields in the YAML *you generated* into `<run_dir>/config/`, since the failure mode is a placeholder left unsubstituted during filling, not a defect in the template itself.

**Don't assume "1 GPU, short wall time" — size this like `fine-tuner` does.** There's no live Ray cluster from an active finetune job to reuse here (that job has typically already finished by the time you're invoked standalone), so you're standing up your own from scratch. Default `platform.number_of_workers`/`resources_per_worker` to match whatever the *finetune* YAML for this project used (read it from `<run_dir>/config/<project_name>.yaml` or equivalent — the checkpoint was trained at that scale, and under-provisioning just means the prediction pass runs on a fraction of the GPUs for no reason), and default `batch_size` similarly per `fine-tuner.md`'s own predict-YAML guidance (match by default; investigate event counts for a better value if there's a clear case). **Report your proposed config to the orchestrator and wait for confirmation before submitting** — same deliberate exception to "don't ask the user anything" as `fine-tuner.md` Step 3, and for the same reason: these values depend on live state (the actual finetune run's scale) that couldn't have been fixed in the plan.

Submitting: compute `<total_gpus>` = `number_of_workers × resources_per_worker["GPU"]` the same way `fine-tuner.md` Step 4 does, and pick the matching job template the same way it does — `job_submit_nersc_template.sh` (single node, ≤4 GPUs) or `job_submit_nersc_multinode_template.sh` (>4 GPUs, needs the multi-node Ray-cluster bootstrap — see that template's header for why a naive multi-node request alone doesn't work) from `.claude/agent-resources/fine-tuner/`, filling `<predict_yaml>` and omitting/skipping the finetune-related placeholders and the `train.py` invocation, or simply running the equivalent `shifter python3 scripts/predict.py <run_dir>/config/predict_<project_name>.yaml` command directly inside your own job script section if it's simpler to hand-write for a predict-only case than to strip down the combined template. Same credential rule as `fine-tuner.md`: no literal API key in any file, export `WANDB_API_KEY` (if this job needs it at all — standalone prediction often doesn't) in the same shell command as `sbatch`.

**Docker**: `python scripts/predict.py <run_dir>/config/predict_<project_name>.yaml`, sized the same way.

**Guard against fully-empty-point-cloud events before submitting.** Before running predict, check whether the predict input contains events where the *entire* visible input point cloud `x` is padding — every slot across every object type in this analysis's slot mapping is `mask=False`. This is a general architectural gap in the shared `PETBody` transformer (not specific to any particular slot composition): its first attention layer produces `NaN` for a query row with zero valid keys to attend to, and that `NaN` survives re-masking (`NaN × 0 = NaN`), propagating through every layer and crashing `Normal.cdf()` during diffusion sampling (or silently corrupting output for non-diffusion heads). It can only happen on uncut predict data — a training cut guaranteeing at least one real object prevents it, but a standalone predict run may target an unselected population where it occurs, even at a very low rate.

Count events in the predict-target parquet where the sum of all point-cloud masks is zero. If any exist, filter them out of the predict input before submitting rather than letting the job crash partway through (an event with no reconstructed objects of any kind can't satisfy any downstream physics selection anyway, so nothing is lost). Report the count/fraction filtered to the orchestrator.

**Monitor to completion before validating** — the same way `fine-tuner.md` Step 5 does: on NERSC, poll `squeue -j <JOB_ID> --noheader`, `ScheduleWakeup` if still listed (check `squeue -p <partition> --noheader | wc -l` once to gauge congestion and pick an interval, e.g. ~1200s if queue depth is in the thousands), then confirm with `sacct -j <JOB_ID> --format=JobID,State,ExitCode --noheader`; on Docker, wait for the background-process completion notification. Only once the job has actually finished, validate per the steps above.

## Output

Report back to the orchestrator (for hand-off to `data-reconverter`):
- Validated `.pt` file path(s)
- Confirmation of structure (feature keys found, point-cloud shape)
- If `Assignment` is active: explicit confirmation `assignment_target`/`assignment_target_mask` are present (or a flagged gap if not)
- If `Classification` is active: explicit confirmation the predicted output is present with the right shape, AND explicit confirmation a usable, distinctly-named ground-truth class label exists in the prediction output (or a flagged gap if not — don't let this surface for the first time at `result-synthesizer`)
- Any issue found and how it was resolved

**Structured reporting**: write a success report (or, if validation genuinely fails and you can't resolve it yourself, a failure report) per `.claude/agent-resources/shared/workflow-state.md`'s schema and failure taxonomy, to `<run_dir>/prediction/attempt_<N>_[failure_]report.yaml`.

**If the orchestrator invokes you in repair/diagnostic mode** (pointing you at a downstream failure report, e.g. from `data-reconverter`, plus this stage's own prior artifacts), read those referenced files from disk per the shared doc's "Repair/diagnostic-mode entry contract" — never assume you remember a previous invocation. Diagnose within your own domain (the prediction `.pt`'s structure/validity) and either fix-and-revalidate (writing a new attempt report with `repair_context`) or write a diagnostic report stating your output already passed validation and the fault lies elsewhere. Don't reach into `fine-tuner`'s or `data-converter`'s own artifacts to fix them yourself — report a suspected upstream cause and let the orchestrator act on it.
