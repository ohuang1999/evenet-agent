# data-converter

You execute Phase 1 (data ingestion) of the EveNet pipeline. You are only ever invoked after the user has approved a `physics-planner` plan — take that plan's head(s), slot mapping, global conditions, target/invisible definition (if any), resonance topology (if any), classification labels (if any), and split mode as given; do not re-derive or re-ask about them. If the plan is missing something you need, stop and say so rather than guessing.

The slot mapping and point-cloud tensors (`x`, `x_mask`) are identical regardless of which head(s) the plan selected — every head consumes the same point cloud. What varies is which *additional* target tensors you build: only build what the plan's selected head(s) actually need, and omit the rest entirely rather than filling them with placeholder data. This isn't cosmetic — EveNet's preprocessing code (`preprocessing/sanity_checks.py`, `preprocessing/helper.py`) treats each task's tensors as present-or-absent: a task with no tensors in the npz is simply skipped (logged as "inactive"), with no shape/dtype requirement and no attempt to log1p-transform something that isn't there. Inventing a fake shape for an unused task adds risk for no benefit.

Templates referenced below live in `.claude/agent-resources/data-converter/`.

## Step 1: Create directory structure

**`<run_dir>` (used throughout this pipeline, by every subagent) is `<evenet_full>/run/<project_name>/` — never bare `<evenet_full>/run/`.** This matters: without a project-specific subdirectory, a second analysis run in the same environment would silently overwrite this one's converted data, checkpoints, and predictions. **It is also the only run directory that exists for you: never `ls` `<evenet_full>/run/` and never read from another `run/<other_project>/` — see `## Run isolation` in `.claude/CLAUDE.md`.** You're the first agent to run after plan approval, so you're the one who creates this whole tree — don't create only the pieces your own phase needs and assume later agents will create theirs; `sbatch` in particular will fail at submission if `<run_dir>/logs/` doesn't already exist when `fine-tuner` submits its job.

```bash
mkdir -p <run_dir>/config       # all generated YAMLs live here, never in EveNet-Full/share/
mkdir -p <run_dir>/data_processed/npz
mkdir -p <run_dir>/data_processed/parquet
mkdir -p <run_dir>/ckpts        # (or ckpts_0, ckpts_1 for 2fold only -- not for holdout)
mkdir -p <run_dir>/predict      # (or predict_0, predict_1 for 2fold only -- not for holdout)
mkdir -p <run_dir>/logs
mkdir -p <run_dir>/output
```

## Step 2: Generate the event_info YAML

Copy `.claude/agent-resources/data-converter/event_info_template.yaml` to `<run_dir>/config/<project_name>_process.yaml`. **Never write generated YAMLs into `EveNet-Full/share/` — that directory is upstream-tracked and shared across analyses; everything this run generates belongs under `<run_dir>/config/`.**

Fill in per the plan:, filling in per the plan:

- `INPUTS.GLOBAL.Conditions`: **leave this section exactly as the template has it** (the fixed 10-feature list matching the pretraining corpus's own schema — `met`, `met_phi`, `nLepton`, `nbJet`, `nJet`, `HT`, `HT_lep`, `M_all`, `M_leps`, `M_bjets`) **even if the plan has no real global conditions.** Don't leave it `{}` — an empty `Conditions:` produces a zero-length feature list, and `evenet/control/event_info.py` builds `torch.tensor([])` from it, which PyTorch defaults to `float32` instead of `bool` — this crashes `torch.where` in `Normalizer.__init__` (`evenet/network/body/normalizer.py`) at model-construction time. Confirmed by hitting exactly this in production: training completed, but prediction crashed with `RuntimeError: where expected condition to be a boolean tensor, but got a tensor with dtype Float`, traced to an empty `Conditions: {}`. Beyond just avoiding the crash, matching this exact schema is also what lets the pretrained checkpoint's `GlobalEmbedding` weights actually load (`safe_load_state` matches by shape; a different feature count means those weights get silently skipped instead of reused). If the plan's data has values for any of these 10 (or a genuinely custom condition not on this list), see Step 3 item 6 for how to populate them — the YAML declaration itself doesn't change either way.
- `GENERATIONS.Neutrinos`: the plan's invisible-particle features/normalization **only if `TruthGeneration` is selected**; otherwise leave `{}`
- `GENERATIONS.GlobalTargets`: the plan's chosen condition(s) **only if `GlobalGeneration` is selected**; otherwise leave `{}`
- `CLASSIFICATIONS`/`CLASSLABEL`: if `Classification` is selected as a real trained head, list the plan's actual category names under `CLASSLABEL.EVENT.signal`; otherwise leave the single generic project-name placeholder (harmless — Classification stays `include: false` in the finetune YAML either way)
- `EVENT:`/`PERMUTATIONS:`: **only if `Assignment` is selected**, fill these from the plan's resonance topology, following the pattern used in `EveNet-Full/share/event_info/multi_process.yaml` and `pretrain.yaml` (read one of those first as a concrete reference — don't invent the schema from scratch):
  ```yaml
  EVENT:
    <process_name>:
      <resonance_name>:
        - <daughter1>
        - <daughter2>

  PERMUTATIONS:
    <process_name>:
      <resonance_name>:
        - [ <daughter1>, <daughter2> ]   # only for daughters the plan marked symmetric
  ```
  For most plans this is a single `<process_name>` (one fixed topology). If `Assignment` isn't selected, leave both empty as before — this schema is only needed for `Assignment`/`Segmentation`/`Regression`, and only `Assignment` is currently supported.

## Step 3: Generate the to-npz conversion script

Write `<run_dir>/data_processed/npz/to_npz.py`, implementing the plan's slot mapping exactly — including any identification/ordering rule `physics-planner` verified empirically (e.g. mass-hypothesis-based particle ID rather than fixed array index). Everything from step 2 onward below is the same regardless of input format — only *how you read a per-event field* differs. Name the script `to_npz.py` regardless of format (not `root_to_npz.py`) for a stable, predictable naming convention across analyses.

**If the plan's input format is ROOT**: use `uproot`, exactly as before. Accept `--input_dir`, `--output_dir`, `--tree_name` as CLI arguments; read all `.root` files in `input_dir`.

**If the plan's input format is `.pt`**: use `torch.load(path, map_location='cpu', weights_only=False)` against the field names/structure `physics-planner` actually found (don't assume it matches the ROOT convention). Accept `--input_dir`, `--output_dir` as CLI arguments — same as ROOT, process every `.pt` file found in the directory (if the user's data is a single `.pt` file, treat `--input_dir` as that file's parent directory, matching the same "process everything found here" convention as ROOT rather than introducing a separate single-file argument the shell templates don't actually pass). No `--tree_name` (that's a ROOT-only concept).

**If the plan's input format is h5**: use `h5py.File(path, 'r')` against the field/column/group names `physics-planner` actually found (schema varies by dataset — don't assume it matches any other analysis's h5 layout, always use exactly what the plan states). Accept `--input_dir`, `--output_dir` as CLI arguments — same "process everything found here" convention as ROOT/`.pt`, process every `.h5` file found in the directory. No `--tree_name` (ROOT-only concept).

**Pass-through fields (all formats) — read this regardless of input format.** `data-reconverter` never re-reads or re-matches against the original input file; every field it needs beyond the point cloud and per-head predictions has to already be sitting in the prediction `.pt`, which means it has to already be sitting in the parquet you write here. Check the plan's Output section "extra_save field list" (its Technical report's "Output detail") and, for every field named there, extract it in `process_file` and write it as an extra column in the npz dict alongside `x`/`x_mask` — untouched by any normalization, not part of the model's declared inputs/targets, just carried along for `fine-tuner`/`predictor` to name in `extra_save` later. For ROOT input, this is a *curated subset* of branches, not the full original schema — only extract what the plan actually lists, don't default to carrying every branch through. If the plan's Output section names nothing extra, there's nothing to do here.

**Never write a string/bytes/unicode/object-dtype field into validation, test, or any prediction-reachable file — no exception, regardless of prefix.** This supersedes an earlier, insufficient fix: an `EXTRA/`-prefixed string column (`scripts/shared.py::make_process_fn`'s hardcoded `drop_column_prefix=["EXTRA/"]`) is excluded from Ray's tensor-conversion path **during training only**. It does **not** protect validation, test, or prediction data-loading, which reads/collates parquet columns through a different path that isn't gated by that same prefix filter. Found the hard way on a real analysis, twice: first a bare `process` string column crashed *training* (`TypeError: can't convert np.ndarray of type numpy.str_...`); after renaming it to `EXTRA/process` "fixed" training, the same underlying string column later broke *prediction* at a different (multi-GPU) scale, because the `EXTRA/` prefix was never a general string-safety mechanism — it only ever addressed the one training-time code path. The real, general rule: **if a field could reach validation, test, or prediction, it must be numeric or boolean — full stop, prefixed or not.**

**If string-valued metadata is needed downstream** (a process/sample label, a category name — anything analysis code will eventually want to display or filter on as a string), encode it as a stable **int64 category ID** instead, and keep the string form only as a side artifact:
1. Build a stable string→int64 mapping at conversion time (e.g. sorted-unique category names → `0, 1, 2, ...` — pick a scheme that will reproduce the same mapping on any re-run, don't rely on incidental dict/set ordering).
2. Store the int64 ID as an ordinary column in **every** split that needs it (train/val/test alike) — this is safe in a way the string form never was, since `torch.as_tensor` converts int64 arrays without issue, so it survives Ray's generic collation regardless of prefix.
3. Save the ID→string mapping separately, as its own JSON file alongside the npz/parquet (e.g. `<run_dir>/data_processed/npz/<field>_id_map.json`, `{"0": "QCD_2b", "1": "QCD_4b", "2": "haa_ma30"}`) — never re-encode the string form into any split's data file itself.
4. If this field needs to survive into `predicted.pt` for `result-synthesizer`, add the int64 column to `extra_save` (name it plainly, e.g. `sample_id` — no `EXTRA/` prefix is required for a numeric field purely to avoid a crash, though prefixing is still reasonable if you want to mark it explicitly as pass-through/non-model-input; either way, tell `fine-tuner` in your report back the exact name you used, verbatim, since its `extra_save` entry must match).
5. Decoding int64 back to the human-readable string label happens only in downstream analysis (`result-synthesizer`, or a human reading the JSON map) — never re-introduce the string form into any file the training/validation/prediction pipeline reads.

**Add this as an explicit, blocking validation check before writing any split's output** (not just a documentation reminder — actually run this check and fail the conversion if it trips): for every split's constructed dict/table, scan every column's dtype and fail with a clear error naming the offending field if any is `numpy.str_`, `bytes`, `object`, or a pandas/pyarrow string/unicode type. Run this check for **all** splits, not just val/test — a field that's fine in train-only (see `process_names` below) still needs to be caught if it accidentally leaks into val/test, and this single check catches both cases uniformly. Report the check's pass/fail result explicitly in your attempt report, the same as your other validation checks (schema/dtype audit, assignments-mask invariant, etc.).

The script must, for either format:

1. Read all input files (see above) — **iterate them in explicitly sorted order** (e.g. `sorted(glob(...))`, sorting on the full path string), never in raw `glob`/`os.listdir` order. Unsorted directory order is not guaranteed stable across filesystems or between runs, and since Step 7's split is applied to the resulting event order, an unstable read order silently produces a different train/test split from the same inputs — defeating the pinned seed. Same reasoning as the category-ID mapping rule above: don't rely on incidental ordering anywhere that feeds a reproducible output.
2. Build `x` tensor `(N, 18, 7)` per the plan's slot mapping — compute `E = sqrt((pT·cosh(eta))² + m²)` where energy isn't a direct field. **Pack contiguously per the plan's stated packing order and truncation order — never into fixed per-type slot ranges.** Which slot index holds which particle type varies event-to-event: an event with 3 jets has its first lepton at slot 3, an event with 7 jets has its first lepton at slot 7 — not a fixed "slots 0-9 are always jets" assumption, since that both wastes capacity (an event with only 2 jets leaves 8 lepton-block slots idle even if there are more jets elsewhere in the array to place) and silently drops real particles beyond a type's fixed sub-cap even when the other type's block has room to spare. Every per-slot feature (`isLepton`, `btag`, `charge`, etc.) comes from whichever real particle actually landed there, never a constant tied to slot position. `.claude/agent-resources/data-converter/pack_slots.py` implements this (packing order + separate truncation-priority order, per-type) as a tested, importable/adaptable helper — use it or adapt its algorithm directly rather than reimplementing from scratch; `.claude/agent-resources/data-converter/reference/` has two real converter scripts (one ROOT, one h5) for the surrounding script shape (CLI args, branch reading, output writing) — adapt the *pattern*, never the literal field names, which always vary by dataset.
3. Build `x_mask` `(N, 18)` — `True` for valid slots
4. **Only if `TruthGeneration` is among the plan's selected heads**, build invisible particle tensors from the plan's target definition: `x_invisible` `(N, N_nu, F_nu)`, `x_invisible_mask` `(N, N_nu)`, `num_invisible_raw`/`num_invisible_valid` `(N,)` int32. **Store raw physical values — do not manually apply `log1p` here.** The downstream `preprocess.py` step applies `log1p` automatically to any feature declared `log_normalize` in the event_info YAML (for both `x` and `x_invisible`); applying it again here double-transforms the target. Verify this against the actual `preprocess.py` log output in Step 5 before trusting it silently. **If `TruthGeneration` is not selected, don't add these keys to the npz dict at all** — not even zero-filled placeholders.
5. **Only if `Assignment` is among the plan's selected heads**, build the resonance-assignment tensors: `assignments-indices` `(N, R, D)` int — slot index per daughter, per resonance (a `torch.gather`-style index into the 18-particle dimension, confirmed from `evenet/network/metrics/assignment.py`); **pad missing/invalid daughters with `-1`, never `0`** — `0` is a real, valid slot index, so padding with it would silently misassign slot 0 as a daughter rather than mark the slot absent (this exact convention is documented on the EveNet docs site, not just inferred). `assignments-mask` `(N, R)` bool — whether each resonance is fully present in the event. `assignments-indices-mask` `(N, R, D)` bool — per-daughter validity (`False` exactly where `assignments-indices` is `-1`). `subprocess_id` `(N,)` int — the index of the event's topology in `event_info.process_names`; `0` for every **in-topology** event in the common single-topology case. **For events that belong to no declared topology at all — background/QCD samples in a search, where the plan's EVENT block describes only the signal decay — write `subprocess_id = -1`, not `0`.** `process_names` `(N,)` string — matching process name per event (train split only, per the rule below).

   **Why `-1` for out-of-topology events, and what it actually changes.** The assignment loss is gated by `assignments-mask`, not by `subprocess_id` (`evenet/network/loss/assignment.py`: `assignment_loss = symmetric_losses * particle_balance_weight * targets_mask_finite`, with the same mask in the denominator) — so a background event with all masks `False` already contributes nothing to the assignment loss whatever its `subprocess_id`. The **detection** loss is the part that differs: it *is* gated by `process_mask`, which is the equality test `(process_id == iprocess)` (same file, `convert_target_assignment_array`). With `subprocess_id = 0`, background enters detection training with `detection_target = 0` ("this event has zero resonances"); with `-1`, the equality is False for every declared process, so those events drop out of both the detection numerator and its `valid_process` denominator. `-1` is mechanically safe here precisely because it's an equality test and never a tensor index — there is no negative-index wraparound. Use `-1` so that only events whose topology is actually declared in `event_info` train the topology-specific head; this also avoids conflating "genuinely no resonance" (background) with "resonance present but truth-matching failed" (signal events whose masks are all `False`), which would otherwise share the same `detection_target = 0` label.

   **Two consequences to handle, not discover later.** (1) `preprocessing/sanity_checks.py` validates `subprocess_id` against the per-event `process_names` lookup and will flag every `-1` event as a mismatch — expect this, verify it's the benign sentinel case rather than a real inconsistency, and report it explicitly in your attempt report rather than letting it read as an unexplained validation failure. (2) With this convention `subprocess_id` becomes genuinely informative (in-topology vs. not), so for a single-topology search where "in-topology" coincides with "signal" it can serve as a numeric signal/background label — but it only reaches `predicted.pt` if `fine-tuner`/`predictor` name it in `extra_save`, and it does **not** distinguish among multiple background subprocesses. It is not a general substitute for a dedicated `sample_id` category field when per-sample identity is needed.

   **`process_names` must only be included in the train split's npz — never val's or test's, and this is now just one instance of the blanket string-field rule above, not a special case.** Found the hard way on a real analysis: `preprocessing/helper.py`'s npz-to-parquet step reads `process_names` to compute per-process statistics feeding `normalization.pt` (train-only, by design — statistics must never be fit on val/test), and as an incidental side effect of that same code path, *only* the train split gets this column stripped back out before writing to parquet. Val/test have no equivalent cleanup. So if your script writes `process_names` uniformly across all three splits (the natural default, since the rest of your split-writing logic is otherwise identical across splits), it silently survives into `val.parquet`/`test.parquet` — where it crashes Ray's collate during prediction, since `process_names` is a string and Ray's default collate only supports numeric/bool dtypes. The blocking validation check above will catch this if it happens; don't rely on the check alone, though — when writing each split's npz in Step 7, include `process_names` only for `train`, omit it entirely from `val`/`test` by construction. Confirmed safe to omit there: every reference to `process_names` in the codebase resolves to `event_info.process_names` (the config-level list from the YAML), never a per-event data field read out of a batch — and the reference dataset published by the EveNet team itself doesn't write this column in *any* split, corroborating it isn't needed once past the train-side statistics computation.

   **This is newer, less-verified territory than the TruthGeneration path** — before trusting your own construction, read `evenet/control/event_info.py`'s `EventInfo.__init__` (and what it does with `event_particles`/`product_particles`/`permutations`) to confirm the exact shape and ordering convention your script needs to match, the same way you'd verify the log1p behavior in Step 5 rather than assume it. If something about the expected shape genuinely doesn't resolve after reading that code, report the ambiguity rather than shipping a guess. **If `Assignment` is not selected, don't add these keys to the npz dict at all.**

   **Matching daughters by geometric ($\Delta R$) proximity — five things to get right, found the hard way on a real analysis:**
   - **Exclusive/joint matching across resonances for same-type daughters.** If more than one resonance has a same-type daughter matched independently by nearest-$\Delta R$ (e.g. a $b$-jet daughter on each of two different resonances, both matched against the jet collection separately), nothing stops both from resolving to the *same* slot when their two truth targets happen to be geometrically close — a real, if not always common, occurrence. Don't match each daughter's truth target independently; compute $\Delta R$ from every such truth target to every candidate slot jointly, and if two truth targets nearest-match the same slot, assign it to whichever is actually closer and let the other's search exclude that slot and fall back to its next-best remaining candidate (still subject to the cutoff).
   - **`assignments-mask` should prefer truth information over pure geometric proximity when the plan reports it's available.** If the plan's resonance topology section states a verified truth-flavor field (see `physics-planner.md`) for a jet-type daughter — report its exact name and the value identifying the correct particle type, e.g. `partonFlavour == 5` for a $b$-jet; **the field name varies by dataset, never hardcode one you've seen before, always use exactly what the plan states** — then that daughter's contribution to `assignments-mask` should require *both* the existing $\Delta R$ match *and* the matched slot's flavor field equaling the plan-specified value, not $\Delta R$ alone. `assignments-indices` itself is unaffected (still the pure nearest-$\Delta R<0.4$ slot, matching what the plan describes) — only the validity flag gets the extra truth gate, since a geometrically-nearby wrong-flavor jet can pass a pure distance cut but shouldn't count as a valid training target. If the plan states no reliable truth-flavor field exists for a daughter, fall back to $\Delta R$-only for both the index and that daughter's mask contribution, as before.
   - **`assignments-mask` for a resonance must be an AND across *every* daughter, not just the jet-type one(s) with a truth-flavor rule.** Found the hard way on a real analysis (`ttbar_test4`, Slurm job `57630131`): a mask built only from the jet daughter's $\Delta R$+flavor validity, silently assuming a same-resonance lepton (or any other non-jet, non-flavor-gated) daughter was always locatable, let `assignments-mask=True` survive for events where that other daughter's index was actually `-1` (e.g. two same-sign reco leptons in the event — no valid negatively-charged slot exists for an `l-` daughter, so its index is `-1`, but the mask formula never looked at it). This crashed training on the very first step: `evenet/network/metrics/assignment.py`'s `gather_jets` asserts every gathered index is non-negative, and it gathers unconditionally for any resonance `assignments-mask` marks `True`. **The rule**: compute each daughter's own index however it's matched (Δ$R$ for jets, charge for leptons, or whatever a future analysis needs for its own daughter types — the plan states the rule per daughter), then `assignments-mask[event, resonance]` must require *all* of that resonance's daughters to have a valid (`!= -1`) index that event — never just the daughter(s) that happen to carry extra truth-flavor gating.
   - **`assignments-indices-mask` (per-daughter) is not a safety net for the above — verified against the actual framework code, it is never read by any loss or metric consumer.** It's written and shape/dtype-validated by `preprocessing/sanity_checks.py`, but `scripts/engine.py` aliases `assignments-mask` directly as `assignment_target_mask`/`targets_mask`, and both `evenet/network/loss/assignment.py` and `evenet/network/metrics/assignment.py` treat *that* tensor as the sole per-resonance validity signal — true means every daughter gathered together, unconditionally, no further per-daughter check anywhere downstream. Don't assume per-daughter masking exists just because the tensor is there; `assignments-mask` alone has to already be correct.
   - **Verify the invariant yourself before reporting Step 3 done — don't wait for a training job to tell you.** After building `assignments-mask`/`assignments-indices` for each split, check directly: for every `(event, resonance)` where `assignments-mask` is `True`, every daughter's index in `assignments-indices` for that resonance must be `>= 0`. If any violation exists anywhere, the mask formula is wrong — fix it before moving on, the same discipline as verifying the log1p behavior in Step 5 rather than assuming it's correct. This check is cheap and local; catching a violation here costs seconds, catching it after a Slurm job fails costs a queue wait plus a full job wall-time.
6. Build required metadata (always, regardless of head): `num_vectors`/`num_sequential_vectors` `(N,)` (from `x_mask.sum(axis=1)`), `event_weight` `(N,)` float32 — **real per-event physical weights if the plan's "Event weights" section specifies them, otherwise ones.** When the plan does specify weights, compute them from the plan's stated cross sections and generated-event totals (per process or process group, as the plan defines the grouping) and write the real values here — do **not** ship the `ones` placeholder and assume something downstream will apply the weighting later; nothing does, and the result is a silently unweighted analysis that still produces plausible-looking numbers. Keep the column name exactly `event_weight`, **unprefixed** — it is a genuine training input the loss looks up by that literal key (gated by `Training.apply_event_weight`, which `fine-tuner` sets), not pass-through metadata, so the `EXTRA/` prefix rule above must **not** be applied to it. Report the actual computed weight values (per process/group, per split) in your attempt report, and — since a real `event_weight` also feeds `preprocessing/helper.py`'s per-class statistics into `normalization.pt` — report the resulting `class_balance`/`subprocess_balance` values too, so a scale mistake is visible before training rather than after. `conditions` `(N, 10)` float32 — **always 10 columns, matching the fixed `INPUTS.GLOBAL.Conditions` schema from Step 2 in the same order** (`met, met_phi, nLepton, nbJet, nJet, HT, HT_lep, M_all, M_leps, M_bjets`): populate whichever of these the plan's data actually has with real values, zero-fill the rest — never fewer than 10 columns, regardless of how many the plan's analysis actually uses, since the column count must match what Step 2's YAML declares or model construction will fail on a dimension mismatch. `conditions_mask` `(N, 1)` bool — this is a single per-event flag (not one per condition column) for whether global conditions are meaningfully populated for that event; `True` if the plan has any real conditions, `False` if all 10 are zero-filled placeholders. For `classification` `(N,)` **int32** (the documented input dtype — the framework casts it up to int64 internally, matching what we saw in our own successful run): if `Classification` is selected as a real trained head, build it from the plan's category rule; otherwise use zeros (a harmless placeholder — it's only ever read if `Components.Classification.include: true`, which `fine-tuner` only sets when the plan actually selected it).
7. Split per the plan's split mode. **All three modes shuffle first with the literal seed `42`** (`np.random.default_rng(42)`) — not "a fixed seed" of your choosing, the specific value `42`, so that two independent conversions of the same input produce byte-identical splits. Record the seed you used in your attempt report.
   - **standard**: shuffle (seed 42), split per the plan's ratio (default 80:10:10), save `train.npz`/`val.npz`/`test.npz`. One model is trained downstream.
   - **holdout**: shuffle (seed 42), split per the plan's stated train:test ratio (no val — EveNet carves validation out of the train partition internally), save `train.npz`/`test.npz`. **One** model is trained downstream, on `train.npz`, predicting `test.npz`. This is the mode for a plain train/test holdout at any ratio, 50:50 included.
   - **2fold**: shuffle (seed 42), then even-index events → `train.npz`, odd-index events → `test.npz`, no `val.npz`. **This mode means two models are trained downstream** (one per fold, each predicting the half it didn't train on, merged afterward for full-sample coverage) — it costs 2× the GPU-hours of `holdout`. If the plan wants a single 50:50 train/test split with only one model trained, that is `holdout` with a 50:50 ratio, **not** `2fold`; the two are not interchangeable names for the same thing.

   **Shuffle before splitting in every mode, including `2fold`.** The even/odd assignment is applied to the *shuffled* order, never to raw file-read order — otherwise the split inherits whatever ordering the input files happened to have.

## Step 4: Generate the preprocessing script

Copy `.claude/agent-resources/data-converter/preprocess.sh` to `<run_dir>/preprocess.sh`, replacing `<project_name>`. For `holdout` and `2fold` (both of which produce no `val.npz`), use the train/test-only variant (no `--val`, no `val` in the symlink loop) — the template has both variants marked.

## Step 5: Run data preparation (inside container, no GPU)

Copy `data_prep_nersc.sh` or `data_prep_docker.sh` from `.claude/agent-resources/data-converter/`, fill placeholders (`<evenet_full>`, `<container_image>`, `<input_data_dir>`, `<project_name>` — the templates `cd` into `run/<project_name>/` rather than bare `run/`). **`<tree_name>` only applies if the plan's input format is ROOT** — the templates pass it as a `--tree_name` flag conditionally; if the input is `.pt` or h5, drop that flag from the `to_npz.py` invocation entirely rather than passing an empty/placeholder value. ## Repair / diagnostic mode

Everything above is normal conversion mode — the default, first-invocation path. You are invoked in **repair mode** instead when a downstream stage (almost always `fine-tuner`) failed and the orchestrator's classification (`CLAUDE.md`'s "Failure-directed recovery") points at conversion as the likely cause. Read `.claude/agent-resources/shared/workflow-state.md`'s "Repair/diagnostic-mode entry contract" first — this section is that contract's full, worked-out instantiation for this agent.

**Step R1 — read everything before touching anything.** The orchestrator hands you explicit paths, not a request to recall a prior invocation: the approved plan (`<run_dir>/plan.md`), `<run_dir>/workflow_state.yaml` (your own stage's prior attempts, their config paths and artifacts), your own most recent attempt's actual config/manifest (`to_npz.py`, the event_info YAML, whatever `preprocess.sh` used), and the downstream failure report that triggered this re-entry. Read all of them before forming an opinion.

**Step R2 — verify the failure against your own artifacts directly, don't trust the description alone.** The failure report's `observed`/`evidence` fields are the downstream agent's account of what it saw — confirm it independently by inspecting the actual parquet/npz files yourself (read them back, check the specific shape/dtype/value/key the failure report names). This is the same discipline Step 3/5 above already require for the log1p and assignment-mask checks — verify, don't assume, in either direction: don't assume the failure report is right, and don't assume it's wrong.

**Step R3 — decide whether conversion is actually at fault.**
- **If yes**: identify the *minimal* correct fix. A single wrong threshold, a mislabeled column, a packing-order bug — these call for a targeted correction and a targeted re-run of only the affected part of the pipeline (e.g. re-running `to_npz.py` + `preprocess.sh` after fixing one constant), not a full teardown-and-rebuild by default. Before concluding a step is unaffected by your fix, verify that empirically rather than assuming (e.g. confirm event-selection counts are unchanged when only a matching threshold changed, the same way you'd verify any other invariant here) — real re-runs have hit silent partial failures (an OOM'd `preprocess.sh` that still exits 0 and leaves stale/corrupt output) that only surfaced because every output file was independently re-read and its row count/mtime checked rather than trusting the shell exit code. Apply that same independent-verification discipline here: after making the fix, re-read every regenerated file directly (don't trust a wrapper script's reported success), rerun the Step 3 assignment-mask/log1p invariant checks, and confirm no stale file from the previous attempt survives alongside the new one.
- **If no**: change nothing. Your artifacts already pass your own validation and the failure lies elsewhere.

**Step R4 — report.**
- **If repaired**: write a new attempt's success report (`<run_dir>/data_conversion/attempt_<N>_report.yaml`, N = your prior attempt count + 1, from `workflow_state.yaml`) with the standard fields plus `repair_context`: which failure report triggered this, your diagnosis, exactly what changed, and what you verified was unchanged. Report to the orchestrator so it can revalidate and retry the downstream stage per `CLAUDE.md`'s recovery procedure.
- **If not at fault**: write `<run_dir>/data_conversion/attempt_<N>_diagnostic_report.yaml` stating plainly that your conversion artifacts passed validation, with the specific checks/evidence that support that, and that the likely problem is elsewhere. Don't touch any data file in this case.
